Developer onboarding · La Pavoiserie

Pavois, layer by layer

You write an application once, in Haxe. It becomes a Mac app with a real menu bar, a Windows app with extra windows, an Android app, a Sailfish app whose cover stays live, a terminal app — and any of them can hoist a panel onto another machine or a paired watch, with its buttons running your closures back home. This document is the map of how that works, from the reactive core up to the wire.

14 repositories 6 backends Haxe 4.3 docs in English · conversation in French

Pavoiser is to dress a ship with flags. In this framework the surfaces of your application are the flags, the machines around you are the masts, and the library that carries a flag to a mast is literally the halyard. An application with every declared surface flying — window here, cover there, panel across the room — is en grand pavois.

The one idea. Declare a surface once, in the shared vocabulary. Every platform mounts it on what it actually has — and where a platform has nothing to mount it on, the build says so, at the declaration, naming the platform.

Everything below is a consequence of taking that sentence seriously: a reactive core that can re-run any surface when state moves; a node model that can describe any tree the same way; a contract each backend signs; and a transport that refuses to send a surface anywhere nobody named.

01 · The stack

Fourteen repositories, each deliberately small. Click a layer to see what it owns — and, just as important, what it never does. The boundaries are where most of the design lives.

Pick a layer

The boundaries are the design

Each library is allowed to know a specific set of things. rui knows nothing about views. nui knows nothing about a platform. dui knows nothing about Android. cafos knows nothing about a Node. When a feature seems to need a library to learn something new, that is the signal to look one layer up or down.

02 · rui — reactivity

Owns state and change propagation, and nothing else. No views, no rendering, no platform.

Three primitives, and one rule. A Signal holds a value and a list of subscribers. An Effect runs a function, records every signal it read while running, and re-runs when any of them writes — recapturing its dependencies each time, so a branch that starts reading a different cell is followed without ceremony. A Lifetime owns what an effect opened and undoes it when the application is over.

var count = new State(0);
new Effect(() -> trace("count = " + count.get()));  // prints 0 now
count.set(1);      // prints 1
count.set(1);      // prints nothing: unchanged
count.peek();      // untracked read — inside an effect, no subscription

State: a signal with a platform half

rui.state.State<T> is what every backend's @:state is built on — one field, one value, one object: this document calls that object a cell. It adds the two things a UI library needs beyond a signal:

  • a platform sink — the native mirror: a Compose MutableState, a Swift AppState, a Qt property. Called directly on an application write, never through the scheduler, so a screen mirrored by a sink updates on the write whatever else is going on;
  • a durable sink — for a cell declared @:state(durable), a write-through to a device-local store shared with the application's own detached surfaces (a widget, an extension). Compare-and-set, per key, because two processes may write.

applyExternal(v) is the platform writing back (a text field the user typed in): effects re-run, the sink stays silent, because the platform already holds the value.

The scheduler, and the batch

Effects run synchronously on every target but JS: a write re-runs what reads it before set returns. That is a tested contract, and two backends depend on it — a terminal has no event loop to defer to, and a Sailfish process reaches Haxe from a Qt callback that will not come back.

Synchronous is right for one write and wasteful for several. Scheduler.batch holds the queue for the length of a scope; effects deduplicate themselves, so a handler that writes three cells re-runs each effect once. Every backend opens a batch where a host gesture arrives — one gesture, one render. State sinks are never delayed by it.

The view rule

A view may only read things that are immutable or observable. A view that reads a plain mutable field compiles, renders once, and goes quietly stale, because nothing can tell it to run again. rui.macros.ViewRule refuses it at compile time, naming the field. Observable: a State, anything implementing rui.Observable. Immutable: a final field, an ImmutableList. Local: a variable inside the view. Anything else is an error.

03 · nui — the node model

Answers one question — what is a node in a view tree? — and provides the contracts a renderer consumes that tree through. It renders nothing.

A Node has a type ("Text", "Button", "VStack"…), an optional key, typed props (PString, PInt, PCallback, and a PReactive thunk for a value that is read live), an ordered chain of modifiers, and children. That vocabulary is the canon: every backend describes its tree in these names — Button/label+onClick, Toggle/isOn — so a tree served from a Mac and one served from a terminal look the same on a wire.

Three contracts, because the host decides

ContractWho holds the treeFor hosts that…Used by
Pull — NodeSourcethe application; the host walks it on demanddiff and preserve widget state themselves (SwiftUI, Compose)sui, aui, cui
Push — NodeSinkHaxe; it diffs and applies targeted patcheskeep stateful widgets and diff nothing (Qt/Silica, WinUI)qui, wui
Snapshot — Snapshot.project / inflatenobody live: the tree as pure datalive in another process or on another machinewidgets, Companion

Neither pull nor push reduces to the other: pull on Qt would destroy and recreate stateful widgets on every change, losing focus and caret; push on SwiftUI would duplicate its diff. So nui normalises both.

The snapshot, and why ids are keyed by place

A live tree cannot leave the process — its props carry closures. Snapshot.project replaces each closure with an integer in an ActionTable and hands back haxe.Json-safe data. Ids are keyed by the node's place (path and prop), never by the closure's pointer, so the button in the same slot keeps its id across re-projections and a tap that raced a fresh frame runs the current closure rather than finding a hole. The table is never cleared between generations — clearing it was exactly how the first interactive companion turned every keystroke into a stale tap.

Two more pieces sit beside it. nui.Follow keeps a snapshot surface current: it runs the content thunk inside an effect, so a write to any cell the tree read re-projects and republishes — the application never says "now". nui.SelfSource is the pull contract over Node itself, which is what lets a backend draw a tree that arrived without converting it into its own views.

04 · kui — native capabilities

Written once, keyed by platform, used from every backend. Reaching the platform no longer means choosing a backend and staying there.

A capability is an interface naming no platform, plus one implementation per operating system at p.platform.<id>.Name. Each implementation carries a @:kuiNative payload saying what the build has to do for it — keyed by toolchain rather than platform, because one OS has several (macOS links through hxcpp under cui, through Xcode under sui):

@:kuiNative({
    hxcpp:  {files: ["native/battery_mac.mm"], libs: ["-framework", "IOKit"]},
    xcode:  {frameworks: ["IOKit"]},
    gradle: {sources: [...], dependencies: [...], permissions: [...], components: [...]},
})
class Battery implements battery.Battery { ... }

// in an application, on any backend:
var battery = kui.Kui.get(battery.Battery);   // null where the platform has none

kui.Kui.get answers null on a platform with no implementation. An application that uses a capability when there is one, and does not when there is not, writes an if — not a define, not a stub that silently does nothing.

Two capabilities ship as their own repositories: kui-store, the durable key-value store behind @:state(durable); and kui-wear, messages to and from a paired watch over the Wear OS Data Layer, including the manifest-declared service that receives while the app is not on screen.

05 · mui — the portable vocabulary

The layer an application writes against. There is no mui.App class: mui is a contract plus a resolver.

Every name — mui.View, mui.ui.Button, mui.App — is an alias resolved at compile time onto the one backend the build selects, and checked against mui.Contract. There is no wrapper at runtime and nothing to step through.

# in the build file
-D mui_backend=aui
--macro mui.macros.Bind.all()

The direction matters, and it was inverted on purpose. mui once held 132 #if (mui_backend == …) branches across 22 files: it adapted to each backend, so it had to know all six. Now each backend declares its own conformance under <backend>.mui.* and mui only resolves and checks. Nothing in mui names a backend, and adding a seventh touches zero files there.

What an application actually uses

Four things, and none requires reading rui's documentation:

  • @:state var count:Int = 0 — an observable cell behind a property: reading count in a view subscribes it, writing count = … re-runs it; count_ is the cell itself, for a control that binds. Add (durable) to keep it across processes;
  • body():View — the main window, always;
  • @:surface(Role) — every other surface: a cover, a menu, a settings pane, a panel on another machine;
  • lifetime.own(…) — anything long-lived, undone when the application is over.

The vocabulary is 29 names: VStack, HStack, ZStack, ScrollView, SafeArea, TabView, Text, Button, Divider, Spacer, Image, ListView, ProgressView, Toggle, Slider, TextInput, ConditionalView, ForEach, and the state, binding and animation types behind them. A backend may leave exactly one out — a terminal cannot draw an Image, and cui says so by providing none.

07 · Surfaces and roles

An application is not one render root. Each thing it can put on screen is a surface, declared by role — never by the native surface's name.

Exposing "cover", "widget" and "live tile" would have made every application name a platform, and several of those are the same thing wearing different clothes. So an application says what a surface is for, and each backend maps it onto what it has. Click a role for what it means on each platform.

Primary

The main window. Implicit — it is body() — and required everywhere. @:surface(Primary) is a compile error saying so.

Live and snapshot: the two corners

A live surface is an effect: the host is on our side of the boundary, and the effect reconciles when the state it read changes. A snapshot surface is drawn by somebody else — a launcher, an extension in another process, a machine across the room — who decides when to draw. Nobody over there will notice a cell moved, so noticing is ours: nui.Follow runs the declaration inside an effect and republishes on every write. The application writes no call, and cannot forget one.

Portable does not mean silent. Each backend states the roles it hosts with @:hostedRoles on its mui.App; a declaration with no host on the target being built stops that build, naming the role and the backend. Accepting a gap is a word in your own source: @:surface(Glance, optional).

A Companion leaves the device, and nothing about writing an application implies wanting that. It takes three deliberate acts, none of them a default: -D mui_carry in the build file, a CompanionServe.serve call, and a pairing — which is the next layer's business.

08 · dui — the halyard

nui.Follow decides when a fresh picture exists. dui decides where it goes, and refuses to decide it by accident.

The library exists because of a defect. Its predecessor lived inside the network library and matched sinks on the bare surface name: an application serving a panel sent it to every machine on the network offering a sink by that name, reconnecting as machines appeared, and the source never named a destination — there was nowhere in the code where it could have. dui makes the target a parameter of the contract.

piecewhat it is
Transport · Target · Channelenumerate who could receive a surface, open a channel to one of them. A channel carries opaque strings both ways.
Fabric · Targetsone transport, many surfaces; the target list as observable state, so a picker in a view follows machines appearing and vanishing
Pairingswhich target each surface was paired to — a durable string per surface, through rui.state.Durable
Hoist · Reachone surface, flown where its reach allows. Paired is the default: with no pairing, nothing leaves. Chosen(fn) for tests; Anywhere is the old behaviour, kept writable and made a deliberate word.
dui.nuithe snapshot wire: {gen, tree} out, {action, arg} back — no socket anywhere, provable in a harness
dui.cafos · dui.wear · dui.muithe transport over CAFOS machines; the transport to a paired watch; every @:surface(Companion) an application declares

Two fabrics taught the contract its shape. A CAFOS machine announces itself and may vanish; a watch is bound once and is simply asleep or awake — so Target.reachable exists, and so does Channel.attached, because a paired fabric attaches inside open, before the caller has wired anything. And on a paired fabric "reachable" is not "listening": the sink announces itself, and the source answers a second attach with a whole tree.

The state never leaves the phone. What crosses is a picture and, on the way back, an integer. The closure runs where the state lives.

09 · cafos — the network substrate

Which machines and surfaces exist here and now, how to reach them, and who may.

An agent runs on each machine. Agents discover each other (UDP broadcast, with a unicast seed across routed subnets), link over WebSocket, and replicate a registry of presence: machines, applications, and the surfaces each offers, keyed surface/<machineId>/<sid>. Identity is Ed25519 with enrolment; a sink applies a per-surface policy — open, net (any authenticated principal of my network), approve, or an explicit allow list. What travels inside a link is an opaque channel: cafos relays frames and never parses them.

To Pavois, cafos is what kui is for platform capabilities: the substrate underneath. It has its own identity, its own documentation in French, and its own roadmap (fluidity — content that follows surfaces as they come and go). It knows nothing about a nui.Node, and that is a boundary the family took a week to restore.

10 · Follow a tap

The best way to hold the stack in your head is to watch one gesture cross it. Step through both cases.

Notice what stays the same across the two: the closure is your closure, it runs where the state lives, the gesture is one batch, and a screen that mirrors a cell updates on the write. What differs is only where the picture goes — which is the whole of dui's job.

11 · The house rules

A few conventions repeat in every library, and they are load-bearing. When a change feels awkward, it is usually bumping into one of these.

What the compiler can know, the compiler says

Never a marker on screen for something knowable at build time. A role with no host stops the build naming the platform; a view reading a mutable field is refused naming the field; a Companion without the carry define does not compile. The one exception is a tree received as data, which degrades with a word rather than a crash.

Identity is the place, never the pointer

Node identity, focus, and action ids across generations are keyed by where a thing sits in the tree. A pointer changes on every rebuild; a place does not.

Degradation is declared, not accidental

@:surface(Role, optional), a backend leaving a contract entry out, a capability answering null. Never a case _: dropping something on the floor.

One record per surface

Its own effect, its own lifetime, its own action table. Never a shared static registry — two surfaces must not share an id namespace.

The picture, not the pipeline

A widget or a remote surface is proven by looking at the screen. A view-tree oracle proves the pipeline ran; it does not prove anyone can see the result — black text on a black widget passed every automated check.

Nothing off-device by default

When a library is both "native app" and "app on a network", the second never arrives with the first. Three deliberate acts before a surface leaves: the define, the call, the pairing.

English in the repositories

Code, documentation, commit messages, tests. Conversation happens in French; the artefacts do not.

13 · Getting set up

Every library is a haxelib registered in dev mode against its checkout, so a change in one is seen by the next build of any other:

haxelib dev rui ~/new-projects/rui
haxelib dev nui ~/new-projects/nui
haxelib dev kui ~/new-projects/kui
haxelib dev mui ~/new-projects/mui
haxelib dev dui ~/new-projects/dui
haxelib dev aui ~/new-projects/aui        # and sui, cui, wui, pui, kui-store, kui-wear

Each library carries its own checks, runnable without a device — start there when you touch one:

libcheckwhat it proves
ruihaxe -cp src -cp test -main StateCheck --interp (also BatchCheck, CleanupCheck, LifetimeCheck)synchrony, batching, sinks, cleanups
nuihaxe -cp src -cp test -lib rui -main Check --interp70 checks: the model, both contracts, snapshot, follow, self source
muitest/surfaces/run.sh, test/durable/run.shthe compile-time refusals, as fixtures that must fail for the stated reason
duihaxe -cp src -cp test -lib rui -lib nui -main Check --interp; test/companion-smoke.sh44 checks with no socket; then the wire end to end with a real agent
cafostest/project-smoke.sh, test/project-remote-smoke.shthe rsx2ui projection path, local and cross-machine

Two habits that have paid for themselves repeatedly: judge a build by its exit code, never by whether a binary exists (a failed link leaves yesterday's executable in place); and when a device is involved, look at the capture.

14 · Glossary

cell
One @:state field, holding one value: a rui.state.State<T> — a signal with get/set/peek, a platform sink and optionally a durable sink. The field itself is a property over it (count reads, count = v writes); the cell is reachable as count_. The unit a view subscribes to, a write notifies, and a durable key persists. Not a record, not a variable, not a node.
surface
One thing an application can put on screen, declared by role. The main window is one; a cover, a menu, a panel on another machine are others.
role
What a surface is for — Primary, Glance, Preferences, Commands, Auxiliary, Companion, Notification — never the native surface's name.
live / snapshot
A live surface is an effect that reconciles; a snapshot surface is a picture somebody else draws when they decide, kept current by nui.Follow.
backend
One of six libraries that render the vocabulary with a platform's real widgets and host the roles it has.
contract
mui.Contract: the list of names a backend must provide, checked when Bind.all() resolves the aliases.
describer
mui.surface.Describe.impl: each backend's way of turning its views into canonical nui nodes, signed at construction.
sink (state)
The native mirror of a cell — a Compose MutableState, a Qt property — called directly on an application write.
sink (surface)
The receiving end of a carried surface: it inflates frames and draws them, and sends action ids home.
action id
The integer that replaces a closure in a snapshot, keyed by the node's place so it survives re-projection.
fabric / transport
Where a surface can be carried (a network of machines, a paired watch), behind dui.Transport.
pairing
A remembered choice of target for one surface. Without one, nothing leaves the device.
capability
A native ability declared once and implemented per platform, resolved by kui.Kui.get.
durable
A cell whose value lives in a device-local store shared with the application's own detached surfaces; @:state(durable).
en grand pavois
Every declared surface flying at once.
